# 数据库

[English](database.md) | **简体中文**

SQLite，驱动为 `rusqlite`，连接由 `r2d2` 池管理；表结构由一份幂等脚本创建，不手工建表。

## 状态都存在哪里

状态存在三处，其中只有一处是本数据库；在库内又分成偏好与记录两类：

| 位置 | 内容 | 为什么在这里 |
| --- | --- | --- |
| `config.json` | `databasePath`、`language`、`colorMode` | 打开数据库之前就要知道，数据库打不开时也能读到 |
| `settings` 表 | 四项偏好：`alarm.defaults`、`pomodoro.durations`、`dashboard.grid`、`sidebar.panels` | 整块读写，从不按字段查询 |
| 其余表 | 任务、标签、专注记录、前台事件、闹钟 | 一行一条记录，要筛选和连接 |
| 浏览器 `localStorage` | 两个布局与主题的镜像 | 只为首屏；以上两处才是准 |

`settings` 的一行是 key、category 与按原样收发的 JSON——后端不持有任何负载的模型（见[表结构](#表结构)）。
写入的界面自己声明类别、自己校验，取用的后端代码把值解析成自己的模型再校验。

清空、导出或导入数据要同时覆盖 `config.json` 与数据库：清空 `settings` 恢复的是偏好，不包括语言与外观。

## 分层

| 文件 | 职责 |
| --- | --- |
| `db/connection.rs` | `Db` 句柄、连接池参数、连接 PRAGMA、`ApiError` 映射 |
| `db/schema.rs` | 完整的 DDL，每次启动幂等执行 |
| `db/upgrade.rs` | 打开本构建的数据库，名字不一致时把旧文件带过来 |
| `db/repository.rs` | 所有模型共用的通用 CRUD 助手 |

启动时 `Db` 被托管进 Tauri 状态，命令通过 `State<Db>` 取用：

```rust
let directory = app.path().app_data_dir()?;
let config = Config::open(&directory)?;
let db = upgrade::open(&config)?;
app.manage(db);
```

## 连接

| 项 | 取值 |
| --- | --- |
| 文件 | `<应用数据目录>/sentryneko-<版本>.db`（即 `%APPDATA%\com.sentryneko.desktop\sentryneko-0.1.0.db`），除非 `config.json` 另指路径 |
| 连接池 | 4 条连接，取用超时 5 秒 |
| 每条连接 | `foreign_keys = ON`、`journal_mode = WAL`、`synchronous = NORMAL`、`busy_timeout = 5000 ms` |
| 时间戳 | UTC 纪元秒 |
| 失败 | `ApiCode::DATABASE`，SQLite 的报错原文放在 `details` |

## 配置

`config.rs` 在数据库旁边维护一个小 JSON 文件，首次运行自动创建：

```json
{
  "databasePath": "C:\\Users\\you\\AppData\\Roaming\\com.sentryneko.desktop\\sentryneko-0.1.0.db",
  "language": "en-US",
  "colorMode": "system"
}
```

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| `databasePath` | 应用打开的 SQLite 文件 | `<应用数据目录>/sentryneko-<版本>.db` |
| `language` | 语言标签，见 `docs/i18n.md` | 检测到的系统语言，兜底为 `en-US` |
| `colorMode` | `dark`、`light` 或 `system`；`system` 跟随操作系统 | `system` |

规则：

- `databasePath` 为相对路径时，相对 `config.json` 所在目录解析；字段缺失则用默认值。
- `language` 缺失、为 `null` 或空白时检测系统 locale，立即尝试保存支持的标签；检测失败或
  不支持时使用 `en-US`。已有文件只补写它缺的字段：保留相对路径、未知键和其他已存值。
  保存失败时仍使用内存中解析出的语言启动，下次启动重新检测。新建配置仍要求写入成功。
  后续启动优先使用已存选择，设置页可以手动覆盖。
- 界面上显示的版本号完全不存这里：它编译进二进制，由 `get_version` 直接回答。这个文件只放
  「打开数据库之前就必须知道」的东西。补写某个字段时其余内容就地保留，相对路径和本构建不认识的
  键都不会被丢掉。
- `language` 为未知标签时回落到 `Language::DEFAULT`，文件保持原样。
- `colorMode` 为未知取值时同样回落到 `ColorMode::DEFAULT`（`system`）。
- 文件无法解析时报 `IO`，解析器原文放进 `details`，且绝不覆盖原文件——手工修好或删除即可恢复。
- 写入先落到 `config.json.tmp` 再改名就位，进程崩溃不会截断配置文件。
- `settings`（下面那张表）存用户偏好；`config.json` 存「打开数据库之前就必须知道」的东西。

## 表结构

表结构共八张表：

| 表 | 存放 | 关键列 |
| --- | --- | --- |
| `todos` | 用户维护的任务 | `title`、`completed`、`completed_at`、`created_at`、`updated_at`、`tag_ids`、`start_at`、`end_at`、`starred_at`、`extra`、`notes` |
| `focus_usage_hours` | 一小时内、某个分类下专注了多少秒 | `hour_start` + `category`（联合主键）、`seconds`（0–3600） |
| `app_events` | 前台应用活动 | `app_name`、`window_title`、`started_at`、`ended_at` |
| `app_usage_hours` | 某个应用在一小时内占据前台的秒数 | `app_name` + `hour_start`（联合主键）、`seconds`（0–3600） |
| `alarms` | 单次或每周提醒 | `label`、`hour`、`minute`、`repeat_days`、`enabled`、`created_at` |
| `settings` | 应用设置：一行一个键，按类别分组 | `id`、`key`（唯一）、`value`、`category`、`updated_at` |
| `tags` | 任务可携带的标签名 | `name`（唯一、大小写不敏感）、`created_at` |
| `todo_tags` | 任务与标签的关联 | `todo_id`、`tag_id` |

标签刻意存两份：`todos.tag_ids` 是标签 id 的 JSON 数组，任务行不必 join 就能回答「带哪些
标签」；`todo_tags` 是另一个方向的索引，`idx_todo_tags_tag_id` 用来查「哪些任务带某个标签」。
`Todo::set_tags` 在一个事务里同时写两边，`Tag::delete` 会把 id 从所有仍列着它的任务缓存里删掉。

`todos.extra` 是任务身上唯一一处「表结构没有命名」的地方：一个 JSON 对象，由列自身的 CHECK 约束
把关，因此只有界面关心的属性不必再动 schema。它刻意不是「列的替代品」——凡是需要排序、筛选、
统计的字段一律建真列，因为这个包是整体读出来的、从不建索引，且每个任务最多 8 KB。写入只经过
`Todo::set_extra`，语义是合并：调用方没提到的键（包括别的版本写下的键）原样保留，`null` 表示删除该键。

`todos.notes` 则是该规则的反例，值得记着：它是一列独立的文本，因为备注是人写给自己的话，长到需要
自己的空间，也是将来搜索第一个会看的地方。目前只是预留：列和读取路径都在，但还没有任何命令写它。

`settings` 是运行期偏好的落脚处，与业务数据分开存放：新增一个设置界面只是加一行，而不是加一张表。
一行的内容是唯一的 `key`、JSON 形式的 `value`、它归属的 `category`，以及 `updated_at`（纪元秒，
与本库其他时间戳一致）；`id` 是代理主键，使得一行可以不靠名字被寻址。`key` 在整张表里唯一，
因此读写单个设置不需要类别；`idx_settings_category` 让「某个主题下的全部设置」变成一次索引扫描。
当前使用的类别有 `pomodoro`、`alarm`、`dashboard` 与 `sidebar`；未来新界面自报的类别会照原样存下，
无需改表。

所有行都经 `Setting` 写入：它拒绝空白或过长的键、空白类别、超大值，以及不是 JSON 的值——对负载只要求
这些，所以 `get_setting`/`set_setting` 能服务任意偏好，新增一个偏好不需要任何 Rust 改动。值本身是什么
意思由别处决定，见[状态都存在哪里](#状态都存在哪里)。

番茄钟时长是 `pomodoro.durations` 这一行（类别 `pomodoro`），值形如
`{ "focusSeconds": 1500, "shortBreakSeconds": 300, "longBreakSeconds": 900 }`；这一行不存在时
按默认值处理。闹钟默认设置是 `alarm.defaults`（类别 `alarm`），值形如
`{ "ringSeconds": 10, "method": "toast" }`——提示音重复多久，以及消息怎么走（`toast`，或
`inApp` 只交给窗口）。

仪表盘布局是 `dashboard.grid`（类别 `dashboard`），值形如
`{ "columns": 4, "placements": { "focus": { "x": 0, "y": 0, "w": 2, "h": 2 } }, "hidden": ["todos"] }`
——网格的列数、按面板 id 存放的每个面板矩形，以及收进组件库的面板；收起的面板保留自己的矩形，所以
放回原处不花任何代价。这一行不存在时表示从未自定义过，页面回落到内置布局。

侧栏布局是 `sidebar.panels`（类别 `sidebar`），值形如
`{ "panels": [{ "id": "todos", "visible": true }] }`——侧栏能显示的全部面板，按绘制顺序排列，
每项带一个决定是否绘制的标记。这一行不存在时表示从未自定义过，按内置顺序显示；写成 `visible` 缺省
的面板视为显示，这也是隐藏功能出现之前的行为。

`app_events` 与 `app_usage_hours` 由同一个前台采集器（`collectors/foreground_app.rs`）写入，它每秒
采样一次前台窗口；前台窗口一变，WinEvent 钩子会立刻唤醒这个循环，不必等下一次采样。每一条上报都
先在一个地方结算——距上次上报过了多久、这段时间是谁的——再交给两个写入者：

- 时间流：一段停留从第一次采样起就有一行，之后每次上报都把它的 `ended_at` 往前挪并重新推送同一行，
  所以正在花的时间当场就能看到，`ended_at` 始终不为空。插入前回查最后一行，同一段（应用和开始时刻
  都相同）就把结束往前挪，而不是再加一行。一行就是一段连续的应用停留，所以每秒重写一次标题的窗口
  也不会把表刷爆。
- 小时桶：把结算出来的秒数按整点切分，加到对应应用、对应小时的那一行上。`AppUsage::record` 先读出
  已存的数字再写回和，封顶 3600；切换应用、跨整点、以及最多三十秒后就落盘，所以被杀的进程最多丢
  这三十秒。
- 两次上报之间超过一分钟，说明循环没有在跑（机器休眠或进程被冻结）：已经计过费的部分结束在
  上一次上报的时刻，缺口本身不记给任何人，进行中的段从「发现循环又在跑」的那次上报重新开始。
- `app_name` 是去掉扩展名的可执行文件名（`chrome`、`Code`），同一个应用在不同版本和安装路径下
  保持同一个值。
- SentryNeko 自己的窗口照常记录：看仪表盘的时间同样花在本应用前面，跳过它只会让事件流留下一段
  不属于任何应用的空白。
- 键盘鼠标五分钟没有输入就视为人不在：在该采样点结束进行中的段，等输入恢复再开新段，因此留在
  前台没人操作的应用不会继续累计时间。默认输出设备有声音、或有全屏应用在跑时不算离开——看视频
  时手可以长时间不碰键鼠，而时间确实花在那个窗口前面。
- 采不到可归因对象时（没有前台窗口、锁屏、进程打不开），同样结束进行中的段。

`AppUsage::ranking` 读取小时桶生成排行：时间窗按整小时计（`from` 所在的那个小时整个计入，这对页面
的预设是精确的，因为它们都从本地零点起算），按应用把各行相加，并丢掉 `LockApp` / `LogonUI`，让锁屏
时间不归到任何应用头上。`AppUsage::backfill` 把「桶出现之前」存下的事件一次性折算进来，且只在桶还
是空的时候做。

`focus_usage_hours` 由窗口通过三个命令触发、由一个分钟级线程（`collectors/focus_tick.rs`）维护：

- 开始一个阶段——专注、短休或长休——在后端开一段，记下阶段、起点、计划长度以及它归属的分类。没有任何行
  记录这一段：正因为不落库，崩溃最多损失当前这一分钟，而不是整轮。分类是自由文本，去掉首尾空白、最长 64
  个字符；不传就是「没起名字的那件事」，存成空字符串。
- 暂停、休息、重置或阶段跑完都会关掉这一段。恢复时新开一段，所以暂停在记录里是一段真实的空白，
  而不是行上挂着的一个状态列。
- 每分钟结算一次进行中的段：它覆盖的每个小时（整小时或部分）在段自己的分类下累加对应秒数。只有专注段
  写入桶；休息段会被推进但不计时。
- 退出时会先停线程并写出最后不满一分钟的部分，然后进程才结束。
- 比一次 tick 更长的间隙——机器休眠、进程被冻结——会被丢弃：段仍然推进到 `now`，所以这段空白
  只跳过一次，不会被之后的每次 tick 反复计入。

热力图（`models/heatmap.rs`）把 `focus_usage_hours` 与 `todos` 汇总成桶：

- 一个桶是本地的一天、以周一为起点的一周，或一个自然月。边界按 Windows 时区规则换算，所以
  一年里两次调钟的那些天长度仍然正确，不会整体偏一小时。
- 窗口内每一天都会返回，空桶也返回，图表不必自己补齐。
- 专注时间读自 `focus_usage_hours`，分钟线程让它保持最新：正在进行中的阶段已经计入。每个小时
  归属到它开始的那一天，所以跨午夜的段留在开始的那天。休息阶段从不进入桶。一个小时读回来是它各分类
  的总和；`FocusUsage::categories` 则把同一批行按分类反过来读，供番茄钟页面按时间窗查询。
- 任务计入 `completed_at` 所在的那一天。`set_completed` 在勾选时写入、取消勾选时清空，所以之后
  重命名一个已完成任务不会把它挪到别的日子。

已完成计数（`models/todo.rs`）按 `completed_at` 读 `todos`：`today` 统计时间戳落在本地零点之后的
已完成任务，`all` 统计全部已完成任务。待办是给以后安排的计划，比例说明不了当天的情况，计数可以。
时间戳这一列出现之前就完成的行没有所属日期，只计入累计。取消勾选会清空时间戳，删除任务会移除整行，
两种情况下两个计数都随之更新。

`alarms` 由 `commands/alarm_commands.rs` 维护、由 `services/scheduler.rs` 读取：

- `hour` 与 `minute` 是本地墙钟时间，而不是某个瞬间，所以换时区后一行仍然保持原本含义。
  `repeat_days` 是星期掩码：第 0 位是周一、第 6 位是周日，`127` 表示每天，`0` 表示单次。
- 单次闹钟在它的时间下一次到来时响一次，响过之后自动关闭；重新打开就再次进入待响状态。重复
  闹钟保持启用，等下一个被选中的星期几。
- 每一行都会持久化，所以未过期的闹钟在应用重启后依然有效：调度器在启动时按当前时钟重新算下一
  个触发瞬间，而不是把它存下来。同理，应用关闭期间已经过去的瞬间不会补响。
- 触发瞬间按 Windows 时区规则换算，所以调钟的那些天长度仍然正确。当天墙钟会跳过的时间
  （春季前拨）就跟着跳过——重复闹钟等它下一个被选中的日子；当天墙钟会重复的时间（秋季回拨）
  只响第一次，绝不响两次。
- 调度器为每个闹钟保存一个触发瞬间，并每秒读一次表，所以新增、编辑、删除或启停都在一秒内生效。
  恰好在读取那一行时到点的闹钟仍会响，最多晚一拍。
- 闹钟怎么响由 `alarm.defaults` 决定，而且是在响的那一刻读取、不是抄进闹钟行里：提示音每两秒响
  一次，直到 `ringSeconds` 用完；`method` 决定要不要向系统申请 Toast，`inApp` 时只靠
  `alarm-triggered` 推送让窗口显示。因此保存默认设置会同时改变所有闹钟。

## 建表

`ensure` 每次启动都在事务里执行整份脚本：缺的表和索引会建出来，已存在的保持原样，重复执行什么也
不改。它是唯一负责建表的地方——无论文件是全新的，还是刚刚才被带过来的。

## 一个版本一个数据库文件

数据库属于哪个版本，写在它的文件名里——`sentryneko-0.1.0.db`；`config.json` 只记路径。每次启动，
`db/upgrade.rs` 读出这个名字，和编译进二进制的版本比对：

| 记下的文件名是 | 会发生什么 |
| --- | --- |
| 本构建的版本 | 原样打开这个文件，除了建表检查什么都不写 |
| 任何别的版本，或者干脆没有版本 | 在旁边建一个以本构建命名的文件，把数据搬过去，然后才把 `config.json` 改写到新路径 |

搬运是刻意做得机械的：两张文件都认识的表按列逐一复制——列取「旧文件有的」和「本构建表声明了的」
交集，所以行保留自己的 id，行与行之间的引用因此继续成立；而本构建新加的列干脆不出现在插入里，
由 schema 自己的默认值补上。搬完之后 `sqlite_sequence` 会被抬到已复制的最大 id 之上，下一个新行
不会复用旧 id。

落到实际效果上：

- 本构建**新增的表**从空开始，和全新安装时一模一样。
- 本构建**新增的列**取它在 DDL 里的 `DEFAULT`；没有默认值就保持 `NULL`。
- **旧文件既不被写、也不被删**。它留在原地。

### 复制失败时

复制是全有或全无的：一个事务，里面任何一步出错——形状差得太远、某一行过不了新约束——整体回滚。
然后：

- `config.json` **不动**。它仍然指着上一个版本的文件，所以「回退」不过是把那个版本重新跑起来。
- 半份新文件被**删掉**。留着它，下次启动就会把它当成本构建的文件原样打开，而一个空数据库比没有
  更糟。
- 一切读数据库的东西都不启动——没有采集器、没有调度器、没有托盘。窗口打开时显示的是回退对话框，
  而不是应用本身；关掉窗口，进程就此结束。

下次启动会从同一个旧文件重新走同一条路，所以手工修好文件、或者回退之后再找机会试，都能接着上次
的地方继续。

降级走同一条路：来自更新构建的文件同样算「不是本构建的」，按同样的方式搬进本构建的文件。

## 仓储助手

| 助手 | 返回 |
| --- | --- |
| `insert` | 新行 id |
| `execute` | 受影响行数 |
| `query_one` | 映射后的单行，无匹配则 `NOT_FOUND` |
| `query_optional` | 映射后的单行，无匹配则 `None` |
| `query_all` | 映射后的全部行 |
| `count` | 首行首列，类型 `i64` |
| `exists` | 查询是否至少匹配一行 |
| `transaction` | `work` 的返回值，`work` 失败时回滚 |

行映射器就是 `fn(&Row<'_>) -> ApiResult<T>`（`RowMapper<T>`），因此模型只需把映射函数作为
关联函数暴露出来，各助手保持通用。

## 新增表或列

1. 在 `db/schema.rs` 里加上 DDL：它是表结构唯一的书写处。每条语句都保留 `IF NOT EXISTS`，这样一次
   启动即使发现只建了一半，也能把剩下的补齐。
2. 给每一列都配 `DEFAULT`（或者允许为 `NULL`），除非某一行没有它就写不下去：已有的库会在下次启动
   被自动带过来，而「`NOT NULL` 又没有默认值」会让整次复制失败——用户看到的是回退提示。除此之外
   什么都不用做——旧文件会留在原地，作为它装过什么的记录。
